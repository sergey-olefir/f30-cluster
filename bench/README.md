# Bench

Run an app that draws through cluster-render on the Mac and watch its display in a browser: the 800x480 HUD (HUD Widgets) or the 1920x720 instrument cluster (Cluster Themes). No car needed.

```sh
node bench/server.js                   # HUD Widgets, then open http://localhost:8078
node bench/server.js cluster_themes    # Cluster Themes
```

The page draws whichever target the app's `app.json` `config.target` names. One app at a time; set `BENCH_PORT` to run a second bench next to the first.

- `server.js` builds the app with the kit (`kit/tools/build.py`, the same build the Store runs on the car) into `dist/`, then runs it.
- It also stands in for `cluster-render`. It listens on a Unix socket, speaks protocol v1 (the same framing and ops as `cluster_render_client.js`), and streams every layer to the page. Protocol mistakes such as bad sizes, unknown refs, layers running off the target or `exclusive` layers show up in the log as warnings or errors.
- `run-app.js` runs the built app inside the kit's stub head unit (`kit/tools/hu-stub.js`, live mode): a fake RHMI and SOME/IP with no BMW SDK. `HUD_CLUSTER_SOCKET` points the app at the bench socket. Its data folder is `bench/.data/<app id>/`, which stands in for the app's `data/` on the car.
- `page.html` draws the layers. Image layers are the app's raw RGBA pushes, and effect layers run the app's real GLSL shader in WebGL. Layers are stacked by class, then z.

**oap-sdk stub:** the kit's build copies an `oap-sdk/` folder into the package. On the car the Store makes the real one from a BMW app. On the Mac, `server.js` writes a stub marked `BENCH_STUB` that throws if anything loads it. It's gitignored. Never ship a build made with it.

**Node version:** the car runs Node 8.16.2. If `my-agent/.cache/node8/` holds it, the app runs on it automatically, and the log line `app started on node-v8.16.2-darwin-x64` confirms it. Set `BENCH_NODE=/path/to/node` to use a different Node. The build itself needs `python3` and `node` on PATH.

**Live reload:** saving any file under the app's folder, `shared/` or `kit/` rebuilds and restarts the app. A layout saved into `bench/.data/<app id>/layouts/<name>.json` overrides the built-in one of that name without a restart: the app's own watcher reloads it, so that path gets tested too.

**Center screen:** the panel shows the status row the car shows, and the settings. A change is pressed on the stub's components (`SET_<KEY>`, a drop-down row or a checkbox press), the same way the car's HMI sends it, so the kit's own settings code handles it. Values are saved in `bench/.data/<app id>/settings.json`; delete the folder to go back to the defaults. Since 2026-11-14 the app's centre screen is a native menu (`shared/menu.js`): the bench does not draw it, but `POST /click` (`{ id, row }`) presses any RHMI component as the HMI does, `POST /hmi` (`{ a: 'back' }`) is the back arrow, and `GET /probe` returns what the app wrote to its components (texts, cells, Visible, checkbox and drop-down values, pictures pushed), the screen stack and the engine's layout. `node bench/test-native-ui.js` drives these (its own data folder via `BENCH_DATA_DIR`, its own shared-screen folder via `SCREEN_DIR`); `BENCH_IMAGE_DIR=<dir>` saves each picture pushed to the HMI as a PNG.

**Signals:** "Demo drive" is the kit's `sim.js`. It has no boost, so boost reads `--`. "Manual" feeds raw SOME/IP values (the fields and scaling the car sends, including FES `displayBoostPressure`), and the kit's `car.js` decodes them. Slider units are rpm, km/h, °C and bar. A manual gear above 0 reads as D. A manual POST to `/signals` may also carry `tyreP` (bar) and `tyreT` (°C), fed as the TPMS fields for all four corners (the rear pair a notch higher). The bench also feeds the car's units as bar and °C, and `program` (`S` or `M`) as the MDrive gearbox display, so the gear reads S3 or M3. The road signs: `limit` (km/h; `0` or none: no limit known; `"end"` or below 0: the end-of-limit sign) and `nopass` (`1`: no overtaking) go in as the raw value of the field `app.json` `config.limit` / `config.nopass` names. While those are `null` (the car then shows BMW's own sign), the bench stands in a field of its own (`bench.SpeedLimit`) so they can still be set, and the "6WB Dials + G20" window over BMW's sign behaves as if the field were wired; `BENCH_LIMIT=off` runs as the car does. Package car3 I: `limit` `"unknown"` or -20 and below is BMW's empty sign "---" (no limit known); `msa` (0 none, 1 active, 2 off, 3 engine stopped by MSA, 4 unavailable; a slider) drives our auto start/stop sign; `tzCar` (the car's offset from UTC in minutes) and `ccMsg` (1: a check-control message shows) go in only through POST `/signals`. They feed the fields `config.msa` / `config.clock` / `config.ccm` name, or the bench's stand-ins `bench.MSA` / `bench.Clock` / `bench.CheckControl` while those are `null` (`BENCH_LIMIT=off`: none).

**Fake persod (driver profiles):** an app whose manifest asks for `de.bmw.infotainment.personalization.UserAccountManager` (`apps/driver_profiles`) gets `bench/fake-personalization.js`: fake providers of UserAccountManager, UserAccount (one instance per slot), UserAccountIntra and SessionManager, registered through the kit emulator's `hu.fakes` hook (`kit/tools/hu-stub.js`), so the app's `signals.proxy` / `get` / `set` / `call` / `on` reach them as they reach persod on the car. It starts with Guest active, a Valet and two local profiles, and behaves as the car does (create into the first free slot, `MAX_NUM_EXCEEDED`, the name setter, `copyGuestData` only while Guest is active and into an unprotected profile, `removeUserAccount`); the header of the file says which parts are seen on the car and which are guesses. It also feeds the active PIA number, engine speed, gear and the PIA transaction. `POST /fake` steers it (`{ current: 'i01' }`, `{ protect: { i02: ['KEYFOB'] } }`, `{ maxUsers: 2 }`, `{ engine: true }`, `{ gear: 'D' }`, `{ piaTx: 'BEGINTRANSACTION' }`, `{ fail: 'copyGuestData' }`, `{ bmwId: 'i02' }`), and `GET /probe` adds `perso`: its accounts and every method call and setter the app sent. `node bench/test-driver-profiles.js` (port 8131) drives these.

**What the bench can't tell you:** whether SOME/IP signals arrive on the car, real HUD brightness, color and blur, GPU timing, how our layers sit next to the CarPlay or Android Auto HUD map, or how the HMI draws the center-screen page. Only the car shows those. The bench also doesn't draw mesh or video layers.

**Backdrop:** for the HUD, a road. For the cluster, a rough stand-in for BMW's own gauges, warning lights, the map window and the solid black gear box the car paints over our layers, to show what the app's layers cover. Where the map window really sits is unverified; the gear box is measured.

**Car view** (the checkbox on the stage, on by default, `?car=0` turns it off): what the driver actually sees, drawn over the composited layers. On the cluster, a dark mask above the hood line (orange curve: the hood hides the top corners, down to y 273 at the left edge and y 240 at the right), BMW's gear box at x 1406-1597 y 342-419 filled solid black, and the seat-belt light rect at x 587-626 y 663-700. On the HUD, a dark mask outside the window seen through the windshield (x 120, y 100, 485x278; it moves with eye position and HUD height). The numbers come from car photos taken Nov 5 2026 (`design/photos/calibration-2026-11-05.json`) and live in one place, `shared/visible.js`: the server sends them to the page in its `hello` event, and the app's `layouts.js` runs the same `check()` on every layout it loads, so the app log warns per widget (`layout "gt3": speed_box: top-left corner 51 px under the hood`, `... overlaps BMW's gear box ...`, `... 30 px outside the visible HUD window ...`). Warnings only; a layout is never refused for this. The layers table flags each layer the check would warn about (`hood`, `box`, `belt`, `window`; hover for the reason).

**Layer cap:** cluster-render draws at most 8 layers per client connection, 32 across all clients (`CompositorLimits` in its `src/compositor.h`; the 9th is refused with "too many layers"), confirmed on the car with the calibration grid's L1..L16 probe on Nov 5 2026. `BENCH_LAYER_CAP=8 node bench/server.js cluster_themes` models it, or set the "layer cap" number in the header (POST `/cap`; 0 = unlimited, the default). Layers past the cap, counted per connection in order of arrival across all targets and kinds (a `drop` frees a slot), get the event `{ ev: 'layer', ref, state: 'waiting', reason: 'bench: over the layer cap of N' }` instead of `shown`, are not drawn, and show in red in the layers table. Changing the cap restarts the app so it registers its layers again; the log says so. The `status` op reply includes the cap and how many layers are over it. The cap is per connection: an app that opens a second socket gets another 8 (hud.js `"conn"`), and the layers table shows each layer as connection:ref.

**Service limits always on:** 32 layers across every connection (`CompositorLimits.layers`; the 33rd is refused with "too many layers") and 16 MiB of pixel memory for every image together, each image counted twice (`Compositor::add_image`; refused with the service's own words "the service's pixel memory is full"). `BENCH_PIXEL_MIB=4` lowers it to try a refusal, 0 turns it off. The header shows the pixel memory in use; the `status` op reply names both. Assets too: the `asset` op (R8 or RGBA8, 1..2048 a side, 32 in all and 16 per connection, "too many assets"; pixel memory twice its bytes) and `bind` (an effect layer's `sampler2D` reads the asset; the page uploads its pixels as a WebGL texture, an R8 byte in `.r`). Assets are listed in the layers table as "asset r8 WxH (not drawn)" and never count toward the layer caps; a `drop` of one still bound is refused with "asset in use".

**Array uniforms:** a `uniform` message with a `type` (`float`, `vec2`, `vec3`, `vec4`, `mat4`) may carry up to 1024 numbers, whole elements of that type (PROTOCOL.md "Uniforms"). The server keeps the type and refuses a count that is not whole elements; the page uploads the whole array with `uniform1fv`/`2fv`/`3fv`/`4fv` or `uniformMatrix4fv`, sized by the shader's own `getActiveUniform` size (an array shows up as `name[0]`, and is looked up by either spelling). Numbers past the shader's array are ignored with one warning in the log. Self-test: connect a second client to the bench socket (the log prints its path), register an effect layer whose shader declares `uniform vec4 u_box[12];` and draws a box per element, and send `cr.uniform(ref, 'u_box', nums, { type: 'vec4' })` with 48 numbers: all 12 boxes must show. Verified Nov 5 2026.

**Pixels:** the event stream carries only a notice per changed rect (`{t:'px', key, x, y, w, h}`); the page fetches the bytes from `GET /px?key=&x=&y=&w=&h=` (raw RGBA rows, the layer's current pixels). Pixels used to ride the stream as base64, and once the engine packed text into 1 MB sheets the page stalled on them (Nov 5 2026). The page reads the stream with `fetch` and a stream reader, not `EventSource`.

**URL options:** `?clean=1` hides the layer outlines. `?only=1` shows just the display at 1:1, for screenshots. `?backdrop=1` starts with the backdrop on. `?car=0` starts with the car view off. `?dbg=1` prints the page's message, pixel-fetch and stream-read counters in the corner of the display (for chasing a stuck page).

**Screenshots from headless Chrome:** a page that joins a running bench first fetches every layer's pixels, and with `--timeout=N` Chrome shot before those fetches landed, so static layers (the grid labels, the L row) came out blank while the layers table said shown. Use a virtual-time budget instead; it lets the fetches settle before the shot:

```
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --use-angle=swiftshader --enable-unsafe-swiftshader \
  --virtual-time-budget=20000 --window-size=1920,720 --screenshot=out.png "http://localhost:8078/?only=1&backdrop=1&clean=1"
```

(800x480 for the HUD.) `?dbg=1` shows whether it worked: `images N px N` means every image layer's pixels arrived.

## twin_dial (round 2, package E)

`node bench/server.js twin_dial` runs the Twin Dial app (the checkout's `apps/twin_dial`). The page's G20 simulation (`?backdrop=1`, `bench/g20/`) draws BMW's lamps, belt group, gear letter and message panel beneath and over it as for any panel app. Without a browser, `tools/shots/twin/` does the same from SPEC numbers (`backdrop.py`).

- **`bench/twin-sim.js`** (installed by `run-app.js` for the app id `twin_dial` only): the SPEC section 11 fields the f30 bench does not feed. POST `/signals` (manual) now also takes `reserve` (1, 0, null), `odometer` (km, null) next to `fuelL`, `range`, `coolant`, `ambient`, `condition`, `engine`, `gear`, `program`. POST `/fake` takes `{ "twin": { trip, units, media, phone, guiding, displayed, sweep, reset } }` (each key replaces that group; `null` is the field's "none" value; `sweep: true` runs the 4 s needle sweep over the manual values). Day/night, the clock, ccList, the cluster's "shown now" number and the frame counter go through the existing `/fake` parts (`dayNight`, `clock`, `clockLocal`, `ccList`, `ccActive`, `ccFrame`), which need the f30-style `config` blocks in app.json. Enums go in by name (`BENCH_ENUM=number`: wire numbers). The trip fields go in as tenths (the scale is unseen, probe P4).
- **A ledger and the "rs" behaviour**: every raw value fed is remembered, and an app that subscribes after a value was fed gets the last one at once (as the car's getter answers). GET `/probe` has `twin`: which field of SPEC 11 the app never watches (`missing`: a typo in app.json), what was fed, the last raw values (text becomes its length), which of `ccList`/`ccActive`/`clock`/`dayNight` app.json names, and the engine's message state (`hud.twinCc`).
- **`BENCH_NOW=<ISO UTC>`**: the app's clock starts there when the app starts (`BENCH_NOW_WRAP=<s>` brings it back every <s> seconds; off by default, a timer that straddles the wrap sees time go backwards). **`BENCH_CONFIG=<JSON or file>`**: merged over app.json `config` before the app starts.
- `node bench/test-twin-sim.js` (port 8205) tests all of it, including a bench whose app does not watch the speed (it must be reported).
- `python3 tools/shots/twin/root.py <dir> [--standin]` makes a bench's own tree (a copy of `bench/`, links to `shared/`, `kit/` and `apps/`); `--standin` (the default while the checkout has no `apps/twin_dial`) uses `tools/shots/twin/standin/twin_dial`, an app of flat blocks that draws SPEC 13.2's layers with A2's faces and window mask, for testing the tools.
